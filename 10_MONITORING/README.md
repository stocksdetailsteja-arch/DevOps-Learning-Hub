# Monitoring And Observability

## Introduction

Monitoring is one of the most important responsibilities of a DevOps Engineer, Cloud Engineer, Site Reliability Engineer, and Platform Engineer.

Applications and infrastructure can experience:

- High CPU utilization
- Memory exhaustion
- Disk space exhaustion
- Server downtime
- Increased response time
- Application errors
- Container failures
- Network connectivity problems
- Database connection failures
- Unexpected traffic spikes
- Security incidents
- AWS resource failures

Monitoring helps engineering teams identify these problems before they severely affect users and business operations.

Observability provides deeper visibility into system behaviour by using telemetry signals such as:

- Metrics
- Logs
- Traces
- Events

This module covers open-source and AWS-native monitoring tools used in modern DevOps environments.

## Module Objective

The objective of this module is to build practical monitoring, visualization, alerting, logging, and incident troubleshooting skills.

By completing this module, you will learn how to:

## Monitoring Vs Observability

### Monitoring

Monitoring identifies known failure conditions by collecting and evaluating predefined signals.

Examples:

- CPU usage is above the configured threshold
- Disk space is below the required limit
- Application endpoint is unavailable
- EC2 instance status check has failed
- HTTP error rate has increased

### Observability

Observability helps engineers understand the internal state of a system by examining its external outputs.

The primary observability signals are:

- Metrics
- Logs
- Traces

Observability is especially useful when investigating complex or previously unknown production problems.

## Core Observability Signals

### Metrics

Metrics are numeric measurements collected over time.

Examples:

- CPU usage
- Memory usage
- Disk usage
- Request count
- Error count
- Request duration
- Network traffic
- JVM heap usage
- Container restart count

### Logs

Logs are timestamped records generated by applications, operating systems, containers, and cloud services.

Examples:

- Application logs
- Nginx access logs
- Nginx error logs
- Linux system logs
- Docker container logs
- Authentication logs
- AWS service logs

### Traces

Traces represent the complete path of a request across multiple services.

Traces help identify:

- Slow services
- Failed downstream calls
- Database latency
- API bottlenecks
- Microservice dependency problems

### Events

Events describe changes or activities inside a system.

Examples:

- Application deployment
- EC2 instance start or stop
- Container restart
- Auto Scaling activity
- Configuration update
- User login failure

## Tools Covered

### Prometheus

Prometheus is used to:

- Collect metrics
- Store time-series data
- Discover monitoring targets
- Evaluate recording rules
- Evaluate alerting rules
- Query metrics using PromQL

### Node Exporter

Node Exporter exposes Linux host metrics such as:

- CPU utilization
- Memory information
- Filesystem utilization
- Disk activity
- Network statistics
- System load
- Operating system metrics

### PromQL

PromQL is the Prometheus Query Language.

It is used to:

- Select metrics
- Filter time series using labels
- Calculate rates
- Aggregate values
- Compare measurements
- Create dashboard queries
- Define alert expressions
- Investigate infrastructure behaviour

### Grafana

Grafana is used to visualize monitoring data.

Grafana dashboards can display:

- CPU utilization
- Memory utilization
- Filesystem usage
- Application request rate
- Application error rate
- Request latency
- Container health
- Kubernetes health
- AWS service metrics

### Alertmanager

Alertmanager processes alerts generated by monitoring systems.

Important Alertmanager capabilities include:

- Alert grouping
- Alert routing
- Alert deduplication
- Alert inhibition
- Alert silencing
- Notification delivery

### Amazon CloudWatch

Amazon CloudWatch is used to monitor AWS resources and applications.

CloudWatch provides:

- Metrics
- Logs
- Dashboards
- Alarms
- Log queries
- Custom metrics
- AWS service monitoring
- Operational visibility

### Elastic Stack

The Elastic Stack is used for centralized data ingestion, search, analysis, and visualization.

Important components include:

- Elasticsearch
- Logstash
- Kibana
- Elastic Agent
- Beats

## Monitoring Methods Covered

### USE Method

The USE method focuses on infrastructure resources.

- Utilization
- Saturation
- Errors

Use it for:

- CPU
- Memory
- Disk
- Network
- Storage systems

### RED Method

The RED method focuses on request-driven services.

- Rate
- Errors
- Duration

Use it for:

- REST APIs
- Microservices
- Web applications
- Backend services

### Four Golden Signals

Important service signals include:

- Latency
- Traffic
- Errors
- Saturation

## Production Monitoring Principles

### Monitor User Impact

Prioritize monitoring that detects customer-facing failures.

Examples:

- Service availability
- Failed requests
- Increased latency
- Login failure rate
- Payment failure rate

### Create Actionable Alerts

Every alert should answer:

- What failed?
- Which environment is affected?
- Which service is affected?
- How severe is the problem?
- What should the engineer check?
- Which runbook should be followed?

### Avoid Alert Fatigue

Do not create alerts for every available metric.

Alert when:

- Immediate human action is required
- Service reliability is affected
- Customer impact is possible
- An operational limit is approaching
- Automated recovery has failed

### Use Meaningful Labels

Useful labels include:

- environment
- service
- team
- severity
- region
- cluster
- instance
- application

Avoid labels with uncontrolled or extremely high numbers of unique values.

### Maintain Runbooks

A runbook should contain:

- Alert description
- Business impact
- Validation commands
- Dashboard links
- Log locations
- Common root causes
- Recovery steps
- Rollback steps
- Escalation guidance
- Post-recovery checks

### Test Monitoring

Monitoring should be tested by:

- Stopping a service
- Generating CPU load
- Consuming disk space safely
- Making a target temporarily unavailable
- Generating controlled application errors
- Verifying alert delivery
- Verifying resolved notifications
- Confirming dashboard recovery

## Monitoring Security Best Practices

- Protect monitoring endpoints
- Restrict Grafana access
- Use least-privilege IAM permissions
- Avoid storing credentials in source control
- Use secure secret-management solutions
- Encrypt communication where appropriate
- Restrict access to sensitive logs
- Avoid exposing confidential values in labels
- Audit dashboard and alert changes
- Rotate notification credentials
- Secure CloudWatch log access
- Review third-party dashboards before importing them

## Monitoring As Code

Store monitoring configuration in Git whenever appropriate.

Examples:

- prometheus.yml
- Alert rules
- alertmanager.yml
- Dashboard definitions
- CloudWatch alarm definitions
- Log ingestion configuration
- Runbooks
- Service-level objectives

Benefits:

- Version control
- Peer review
- Change history
- Repeatable deployment
- Environment consistency
- Rollback support
- CI/CD validation

## Cost Optimization For AWS Labs

To control AWS learning costs:

- Use small lab instances where suitable
- Stop or terminate unused EC2 instances
- Delete unused EBS volumes
- Remove unnecessary snapshots
- Delete unused load balancers
- Review CloudWatch log retention
- Remove unused custom dashboards and alarms
- Avoid collecting unnecessary high-volume logs
- Avoid publishing unnecessary custom metrics
- Clean up resources after completing screenshots
- Verify the AWS Billing dashboard regularly

Before terminating an EC2 lab instance:

- Save configuration files
- Export dashboard definitions
- Copy important commands into Markdown files
- Save screenshots locally
- Push documentation to GitHub
- Confirm that no required files remain only on the instance
